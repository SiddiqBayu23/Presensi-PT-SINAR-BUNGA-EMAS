# Security Specification — PT Sinar Bunga Mas HRIS (Firestore Zero-Trust)

## 1. Data Invariants
1. **Master Gate & Global Default Deny**: Every unmatched path is denied (`allow read, write: if false`).
2. **Verified Email Identity**: Every authenticated read/write requires `request.auth != null && request.auth.token.email_verified == true`.
3. **No Self-Assigned Roles**: Non-admin employees can only create `/employees/{uid}` where `employeeId == request.auth.uid` and `role == 'employee'`. Only verified HRD admins (`fikriramadhan998@gmail.com` or `/admins/{uid}`) may assign `role == 'hrd'` or `role == 'supervisor'`, modify salaries/leave quotas, or manage `/admins/{adminId}`. Three roles exist: `hrd` (admin, must be in `HRD` division), `supervisor` (team approver), `employee` (karyawan). Account provisioning for email/password login is admin-only (menu Admin → Data Karyawan, which creates the Firebase Auth user on a secondary app instance with `uid == employees/{uid}`); non-admin profile creation remains limited to the bounded self-onboarding tier used by verified Google sign-in.
4. **Supervisor Routing & Tier**: `supervisorUid` is an optional field on `employees`, `attendance`, `leaves`, `overtimes`, `shiftSwaps`, and `exitClearances`; it must be empty or reference an existing employee whose `role == 'supervisor'` and whose `division` equals the record's `division` (`isValidSupervisorAssignment`, evaluated only in create/update because it calls `get()`/`exists()`). Attendance clock-in additionally pins `supervisorUid` to the value on the employee's own profile. A supervisor may review (status/reviewedBy/updatedAt only) a submission only when `existing().supervisorUid == request.auth.uid` and the reviewer is not the submitter; supervisors may also adjust `leaveQuota` and `shiftCode` of direct reports in the same division. `allow list` tiers never call `get()`/`exists()`: they compare `resource.data.supervisorUid == request.auth.uid` (employees, attendance, and the four request collections).
5. **PII Isolation**: `/employees/{employeeId}` holds employment terms plus contact PII (email, phone, address) and `photoUrl` (square profile photo as an image data URL, capped at 400000 chars; owner or HRD admin may set it). Single-doc `get` is strictly limited to `isOwner(employeeId) || isAdmin()`. `list` queries are strictly limited to `resource.data.uid == request.auth.uid || resource.data.supervisorUid == request.auth.uid || isBootstrapAdmin()` (zero `get()`/`exists()` inside `allow list`), so a supervisor only sees direct reports they are assigned to. Identity and payroll PII (`ktpNumber`, `kkNumber`, `fullNameKtp`, birth data, `ktpAddress`, `gender`, `motherName`, `workRegion`, `maritalStatus`, `childrenCount`, bank details, emergency contact, `lastEducation`) lives in the separate `/employeeProfiles/{employeeId}` collection: owner or HRD admin may create and update a profile, while `get` remains owner-or-admin and `list` remains owner-only or `isBootstrapAdmin()`. Scanned KTP/KK lives in `/employeeDocuments/{uid}_{ktp|kk}` and may only be read, created, updated, or deleted by its owner or HRD admin. The split keeps the supervisor-visible roster document free of identity data and keeps each write inside the 1000-expression rule budget.
6. **Global Consistency Invariant**: Every operational record (`attendance`, `leaves`, `overtimes`, `shiftSwaps`, `exitClearances`, `schedules`) MUST reference an existing employee profile via `exists(/databases/$(database)/documents/employees/$(incoming().uid))` on create.
7. **Terminal State Locking**: Once a `leave`, `overtime`, `shiftSwap`, or `exitClearance` transitions to `'Disetujui'` or `'Ditolak'`, non-admins cannot mutate it. Once an `attendance` record has `clockOutTime != ''`, non-admins cannot overwrite it.
8. **Temporal Integrity & Immutability**: `createdAt == request.time` on create; `updatedAt == request.time` on update; `uid`, `nik`, and `createdAt` remain immutable on update.
9. **Strict Key & Size Enforcement**: Every create enforces `hasAll` + `hasOnly`; every update is wrapped in `isValid[Entity](incoming())` and uses action-based `affectedKeys().hasOnly(...)`. Every string has `.size()` bounds; `exitClearances.checklist` is strictly bounded `1..10` with index-0 map validation.

## 2. The "Dirty Dozen" Adversarial Payloads (Must Return PERMISSION_DENIED)
1. **Unverified Admin Email Spoof**: `{ auth: { uid: "attacker", token: { email: "fikriramadhan998@gmail.com", email_verified: false } } }` reading `/employees/victimUid`.
2. **Self-Assigned HRD Privilege Escalation on Create**: Creating `/employees/u1` with `{ uid: "u1", role: "hrd", ... }` as non-admin.
3. **Shadow Field Injection ("Ghost Field")**: Updating `/employees/u1` with `{ phone: "0812", isSuperAdmin: true, updatedAt: serverTimestamp }`.
4. **Cross-User PII Read**: Authenticated verified user `u1` requesting `get /employees/u2`.
5. **Blanket Collection Scraping**: Authenticated verified user `u1` executing unfiltered `list /attendance` without `where('uid', '==', 'u1')`.
6. **Salary & Leave Quota Tampering**: Employee `u1` updating `/employees/u1` with `{ baseSalary: 99999999, leaveQuota: 999, updatedAt: serverTimestamp }`.
7. **Identity Spoofing on Attendance Create**: Employee `u1` creating `/attendance/att-1` with `{ uid: "u2", ... }`.
8. **Orphaned Record Creation**: Authenticated verified user `u_ghost` (no `/employees/u_ghost` doc) creating `/leaves/lv-1` with `{ uid: "u_ghost", ... }`.
9. **Self-Approval State Shortcutting**: Employee `u1` creating `/leaves/lv-1` with `{ status: "Disetujui" }` or updating an existing leave to `status: "Disetujui"`.
10. **Terminal State Mutation**: Employee `u1` updating `/exitClearances/ex-1` checklist after `existing().status == "Disetujui"`.
11. **Resource Poisoning (Oversized ID & String)**: Creating `/attendance/` with a 150-char document ID or a 5,000-char `clockInAddress`.
12. **Client Timestamp Forgery**: Creating `/overtimes/ot-1` with a backdated client timestamp (`createdAt != request.time`) or mutating `createdAt` during update.
13. **Cross-Route Supervisor Review**: Supervisor `sp_security` updating `/leaves/lv-2` whose `supervisorUid == "sp_other"` or whose `division` differs from `sp_security`'s own employee doc.
14. **Self-Routed Approval**: Employee `u1` creating `/leaves/lv-1` with `{ supervisorUid: "u1" }` or `{ supervisorUid: "peer_uid" }` where the target is not an active `supervisor` in the same division (`isValidSupervisorAssignment`).
15. **Supervisor Payroll Escalation**: Supervisor `sp` updating direct report `/employees/sub` with `{ baseSalary: 99999999 }` or `{ role: "hrd" }`; supervisors may only change `leaveQuota` and `shiftCode` of direct reports.
